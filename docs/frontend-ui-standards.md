# 前端设计与组件复用规范

本规范适用于 ProductionAssistant 后续所有前端开发、组件引入、页面迁移和 UI 修复。实施前必须阅读；不能以构建通过代替设计与业务验收。

## 1. 统一设计来源与职责

| 来源 | 职责 |
| --- | --- |
| [shadcn-admin](https://github.com/satnaing/shadcn-admin) | 应用外壳、导航结构、Sidebar、Header、页面布局和整体视觉设计 |
| [shadcn/ui](https://github.com/shadcn-ui/ui) 与[官方组件文档](https://ui.shadcn.com/docs/components) | Button、Input、Dialog、Table、Select、Sheet、DropdownMenu、Tooltip 等基础组件 |
| ProductionAssistant | 业务数据、页面内容、功能流程、业务适配代码及 .NET 服务 |

**界面视觉以 shadcn-admin 为准，基础组件以 shadcn/ui 为准，业务内容以 ProductionAssistant 为准。**

当前已移植组件的上游提交、文件对应、许可证及必要适配见 [shadcn-admin 移植说明](third-party/shadcn-admin.md)。引入组件时以兼容并核对过的源码为依据，不能仅凭截图仿制。

## 2. 优先复用官方基础组件

1. 编写 UI 前，先查询 shadcn/ui 官方组件文档及本仓库已有组件，确认是否已有对应能力。
2. 官方已有的组件，优先通过与现有技术栈兼容的 shadcn CLI 安装，或基于官方源码集成；安装前核对版本和依赖兼容性。
3. 禁止自行重新开发已有的 Button、Dialog、Table、Input、Select、Sidebar 等通用基础组件。禁止仅通过自定义 CSS 仿制官方组件，代替实际组件复用。
4. 官方组件不能直接满足需求时，优先使用官方推荐的组合方式。只有确实无法满足时，才考虑新增通用组件，并在实施前报告原因及替代方案。
5. 允许开发日报任务列表、模板编辑工作台、生产数据表格等业务组件，但必须优先组合已有基础组件。
6. 不允许因个人设计偏好随意改变上游组件的基本视觉与交互，也不允许为了减少依赖而重新实现官方已提供的通用组件。
7. 不允许为了使用组件而无条件升级 React、Vite、TypeScript 或测试框架等整个技术栈；确需调整时，先说明兼容性依据和影响范围。

## 3. 保留 shadcn-admin 的定制

shadcn-admin 部分组件已在 shadcn/ui 基础上定制，不能仅因官方版本更新就无条件覆盖。

- 涉及这些组件时，先核对 shadcn-admin 实际使用的源码和样式，优先保持其原有视觉、布局与交互。
- 确实需要适配时，记录修改原因和与上游的差异，不另行设计一套不同风格的组件替代。
- 特别核对 Sidebar、主题、菜单、弹窗及页面容器；已有本地适配也需评估后保留，不能被重新安装覆盖。

## 4. 统一视觉语言与字体

后续业务页面遵守 shadcn-admin 的设计体系，统一颜色和主题变量、字号层级、按钮和输入框、表格和弹窗及菜单、间距和圆角及边框、交互反馈、图标来源和暗色模式适配。图标沿用项目已使用的 Lucide 体系。

不允许每个业务页面形成独立视觉风格。没有明确需求时，不自行增加渐变、装饰性卡片、复杂动画或其他上游不存在的元素。

**当前试验字体：Inter Variable + Noto Sans SC Variable，最终选择待用户在 Electron 中验收确认。**

- 当前试验顺序为 `"Inter Variable", "Noto Sans SC Variable", sans-serif`：英文、数字优先 Inter，中文回退到 Noto Sans SC；使用已本地安装的可变字体。
- 字体试验保留 shadcn-admin 的配色、字号层级、字重、组件尺寸及间距，不使用额外字重、阴影或缩放掩盖问题，不添加永久字体切换功能。
- 字体核查需同时检查 computed 样式、实际资源加载和渲染字形来源；仅有 CSS 声明或 `document.fonts.check` 不能证明实际中文字体正确。
- 用户确认后再将字体选择更新为正式规范，不能提前认定试验方案已获验收。

迁移按授权阶段推进。尚未迁移的旧页面、iframe 和旧 portal 可暂时保留现有样式边界；不能通过全局 reset 或覆盖旧 token 强行统一。完整主题适配按对应阶段验收，不将过渡状态作为新增独立风格的依据。

## 5. 保留业务架构与调用链

保持现有 `React → Bridge → Electron IPC → Sidecar → .NET` 架构，并兼容共享前端的 WinUI 宿主。

- 保留业务 query 路由、`loadId` 语义、业务状态与数据逻辑、统一 Bridge、Sidecar 操作权限、数据和配置格式以及自动化任务运行逻辑。
- 保留现有懒加载、Suspense、LoadBoundary、RouteReady、设置与错误反馈；UI 移植不能变成业务逻辑重写。
- 不得为了使用上游 UI 直接复制其认证系统、用户或团队管理、演示数据、Axios 请求体系、TanStack Router/Query、Zustand 等与本项目业务无关的运行体系。

## 6. 组件维护、来源与许可证

每次新引入组件，必须在可由 Git 跟踪的来源文档中明确：

- 组件名称，以及来自 shadcn/ui 还是 shadcn-admin。
- 对应上游版本或完整提交，以及可核对的源码路径或链接。
- 本地适配内容、修改原因及与官方或上游版本的差异。
- 是否需要额外依赖，以及实际采用的兼容版本。
- 适用许可证，按实际复用代码的许可要求保留必要版权声明及许可证文本。

不无理由维护多个功能相同的基础组件。更新或重新安装前先核对已有适配；来源和差异记录随代码一起维护，不能只保存在被忽略的本机文档中。

## 7. 验收与交付

每个 UI 阶段必须分别报告以下结果：

1. 构建和自动测试是否通过，包括适用的前端测试、完整 `verify.ps1` 及共享 dist 检查。
2. 组件与布局是否符合 shadcn-admin 和实际采用的 shadcn/ui 源码设计。
3. Electron Development 实际窗口是否正常，包括窗口尺寸、内容滚动、路由刷新及字体加载；共享前端还需关注 WinUI 兼容性。
4. 原有业务是否正常；浏览器无宿主检查或 mock 不能代替真实 Bridge / Sidecar 业务验收。
5. 是否通过用户人工视觉验收。未做的项目明确标为待验收，不能因为构建通过就宣布 UI 完成。

不再为每一批 UI 迁移自行生成第二套独立 HTML Demo。优先在真实 React 应用中开发，由用户在 Electron 中验收；如仓库现行有效规则明确要求其他前置流程，先报告冲突。

本规范不扩大运行、数据写入、部署、提交或发布授权；具体流程仍遵守项目 AGENTS.md 和当前任务范围。未经授权不启动 Electron / WinUI 或操作正式数据。
