# 腾讯文档自动填报：正式接入前的补充约定

日期：2026-09-09。对应评审意见 3、4、7、8、9、10。

本文是设计补充，不表示正式功能已经实现。使用者已随机测试 v5 的若干数据并反馈写入正常；这证明了当前页面的内容编辑区直写路径，不等于自动保存、异常恢复和无人值守登录已验收。原方案（含第 32 节）尚未在当前仓库中找到，取得原文后应将这些约定并入对应章节。

## 现状与拟实现范围

当前 Demo 的真实路径是名称框定位 → 读取内容编辑区 → 确认目标没有已有数据 → 聚焦内容编辑区 → 输入对应数值 → 检查输入结果 → Enter → 重新定位回读 → 最终刷新回读。继续沿用这条已验证路径，不再使用 F2、Tab 或方向键探测。

当前 `browser.cjs` 在自动模式末尾等待 2 秒再刷新；额外状态模式只等待配置的 `saved` 元素可见，没有保存状态转换关联，也没有网络重试。正式接入需要补上本文的保存确认与有限重试。本文不修改 Demo 行为，也不迁移正式业务代码。

## 3. 保存确认：页面状态是辅助证据，重新打开后的数据是最终证据

必须区分三个阶段：内容编辑区出现输入值、Enter 后页面内回读一致、重新打开文档后回读一致。前两项不代表服务端已保存。

优先使用页面实际存在、人工确认语义的“正在保存 / 已保存”状态。配置为两个精确状态条件；不能用始终可见的状态栏容器代替“已保存”，也不能把“正在保存”消失单独视为成功。当前尚无已验证的状态选择器，不虚构选择器。

处理约定：

1. 在提交前开始观察保存状态，记录提交时刻。若捕获到本次提交后的“正在保存 → 已保存”，且已无保存中状态，可以立即进行最终重新打开和回读，不额外固定等待。
2. 保存过快可能没有捕获到“正在保存”；不要强制要求一定看到它。若仅见原有“已保存”，不能据此证明本次提交已保存，改走下面的退化路径。
3. 状态元素未配置、无法可靠区分或短时间未捕获变化：固定等待作为退避间隔，随后重新打开并回读。本轮建议初次等待 2 秒，仍未一致时最多追加两次只读确认，间隔 2 秒、4 秒；所有尝试受一次保存确认的总截止时间约束，建议 30 秒。这些数字是初始运行参数，不是保存证据。
4. 若明确仍在“正在保存”，在总截止时间内等待，不主动刷新中断该状态；超时报告 `SaveUnconfirmed`。若显示明确的保存错误，保留原始状态并报告，不把消失当成成功。
5. 重新打开前，必须已经通过 Enter 提交，且不处于尚未提交的编辑状态。刷新后重新检查文档和 Sheet 身份，并回读所有本次已提交地址。只有值全部一致才完成保存确认。

页面内刚提交后的读值也允许在同一操作截止时间内短暂轮询，避免页面渲染延迟被误报为模板错误；不重新输入。恢复读取发现不同的非空内容时立即停止，不覆盖。截止时仍为空或旧值，报告保存未确认和具体地址，不声称写入失败后可以直接重试。

同一文档在一次任务内串行写入；最终保存确认可覆盖本批已提交的全部地址，避免每个格子都重复执行整段固定等待。页面状态变化也可能来自其他协作者，所以最终回读不能省略。一次只读确认不能证明整个批次具备事务性。

## 4. 合并锚点与隐藏列

模板配置从一开始就要求：**每个合并表头锚点必须使用合并区域左上角的 A1 地址**。配置保存时校验 A1 格式、必填项和模板映射；如果页面没有可靠的合并范围信息，不能宣称代码已自动证明“这是左上角”，需要模板负责人确认并通过非空预期值校验。

例如 V24:W24 是同一个日期合并区域时，型材、板材的日期校验均读取 V24；不能为板材日期读取 W24。前提是模板确认实际合并范围确实如此。公司名等锚点同理。锚点允许多个业务项复用同一左上角地址，目标数据地址仍必须互不重复。

隐藏列不引起 A1 地址重新编号。计算列时使用完整工作表列坐标，不按屏幕可见列的位置推算，不因为读到空值就尝试向左寻找“最近有值的格子”。

锚点预期值不能为空；读到空值或与预期不同，作为确定性模板校验错误停止，并指出锚点名称、地址、期望值和实际值。目标数据格若本身合并，则也必须显式配置实际左上角地址；不能静默把普通目标映射到附近合并格。模板版本变更后重新验收这些映射。

## 7. 有限重试：按故障原因和是否已经写入共同决定

重试放在腾讯填报业务内部的具体安全操作周围，不放在通用 `AutomationTaskRunner` 外层，不重跑整个 Handler。

| 情况 | 处理 |
| --- | --- |
| 写入前的网络中断、加载超时，且未发现登录/权限/模板错误 | 最多重试 2 次只读操作，退避 1 秒、2 秒；总计最多 3 次尝试 |
| 名称框定位或内容读取超时 | 可以在重新确认文档、Sheet 后重试只读定位/读取；不能以超时为理由重写数据 |
| 登录失效、无权限、配置无效、模板/锚点不匹配、目标已有内容 | 确定性错误，直接停止，不重试、不反复发起登录 |
| 页面加载正常但指定控件始终不存在 | 控件配置或页面结构问题，停止；不能把所有找不到控件的超时都归类为网络抖动 |
| 开始输入后断网、Enter 调用超时、保存超时或回读不一致 | 写入结果可能不确定，只允许读取恢复；不得自动重新输入、重提 Enter 或整批重跑 |
| 用户取消或主动关闭浏览器 | 立即停止，不自动重启浏览器或恢复写入 |

进入输入动作前记录当前地址、预期数值和操作阶段；提交后记录已确认地址。若本次运行有提交记录，恢复读取与预期相同可确认该次提交成功；若没有本次提交记录，即使目标已有相同数字，也仍遵守“不写已有数据”的冲突规则。

多个重试机制共用总截止时间，避免“网络重试 × 保存重试”相乘。保留原始异常用于技术详情，另记稳定的业务错误类型、阶段、重试次数、业务日期、已完成地址和结果不确定地址。未知异常不能一律包装成“模板校验失败”。

自动恢复成功不触发失败通知；重试耗尽或确定性失败只返回一次最终结果，由现有 Runner 通知。业务实现默认不自行再发送同一条失败通知。不得在不确定结果中报告成功，也不自动覆盖或回滚远端数据。

## 8. 业务日期：一个纯函数，一次解析，整轮固定

正式腾讯填报采用以下明确默认规则：业务时区固定 UTC+08:00；`previous_day` 指该业务时区的前一个自然日，周末和节假日照常处理，不解释为“上一个工作日”。工作日历不在首版范围内，后续如需要必须显式增加日历规则，不能悄悄改变 `previous_day` 含义。

使用 `DateTimeOffset` 表示触发时刻，返回 `DateOnly`，不接受时区含糊的 `DateTime`，不在函数内部调用 `Now`。拟定函数如下（设计示例，尚未加入生产源码）：

```csharp
static DateOnly ResolveBusinessDate(DateTimeOffset triggerTime, string mode)
{
    var today = DateOnly.FromDateTime(
        triggerTime.ToOffset(TimeSpan.FromHours(8)).DateTime);
    return mode switch
    {
        "previous_day" => today.AddDays(-1),
        "today" => today,
        _ => throw new ArgumentException("不支持的业务日期模式", nameof(mode))
    };
}
```

当前 `AutomationTaskExecutionContext` 只有 `StartedAt`，没有原计划触发时刻；Runner 在进入 Handler 前设置它。首版将 `context.StartedAt` 作为本次触发时刻快照，在腾讯填报入口解析一次，再把结果显式传给取数、模板地址计算、写入、记录和重试。不能在重试或逐格循环里重新计算日期。

这意味着：跨日延迟启动按实际开始日取前一天，而不是按原计划日回推。首版不自动补齐停机期间漏跑的日期。历史补填由用户明确选择 `businessDate`，该显式日期优先于 mode；跨日重试继续沿用本轮已确定的日期。计划触发时刻如将来需要支持，应独立传入，不能假装当前 `StartedAt` 已表达了它。

| 输入 | mode | 预期业务日期 |
| --- | --- | --- |
| 2026-09-09 07:00 +08:00 | previous_day | 2026-09-08 |
| 2026-09-08 16:01 +00:00 | previous_day | 2026-09-08 |
| 2026-09-07 07:00 +08:00（周一） | previous_day | 2026-09-06（周日） |
| 2027-01-01 07:00 +08:00 | previous_day | 2026-12-31 |
| 2028-03-01 07:00 +08:00 | previous_day | 2028-02-29 |

源码中已有 `NotionFillTaskHandler.ResolveBusinessDate(DateTimeOffset)`，按机器本地日期取前一天；这是既有业务语义。此次不顺手修改它，也不为了一个新业务把日期规则扩散到通用 Runner。腾讯日期函数先留在腾讯业务模块内，只有真正共用时才提取。

## 9. Browser / Client 的职责

下列名称是正式接入的拟定组件；当前 Demo 的 `BrowserSession` 尚未拆分。

| 组件 | 拥有的职责 | 不承担的职责 |
| --- | --- | --- |
| `TencentDocsBrowser` | 浏览器进程与专用 Profile 生命周期、登录状态的唯一判断实现、交互登录入口、会话有效性检查、资源关闭 | 不认识公司/日期/材料，不计算 A1，不读写业务单元格 |
| `TencentSheetClient` | 使用已认证的浏览器上下文打开指定文档和 Sheet；名称框定位、内容编辑区读写、保存状态等待和回读 | 不启动第二个浏览器，不管理 Profile，不自行扫码/续登，不拥有业务日期规则 |
| 腾讯业务服务 | 串行执行、业务取数、日期快照、计划与锚点验证、分阶段有限重试、运行记录 | 不复制浏览器登录判断，不修改其他 TaskType 的业务流程 |

Browser 提供已认证会话；Client 持有借用的上下文/页面，生命周期由 Browser 管理。打开文档后可能再次出现登录页，统一调用 Browser 拥有的会话检查，Client 不另写一套登录页面判定。无人值守运行发现登录失效直接报告需要用户登录，不在任务内无限等待扫码。

文档和 Sheet 身份验证属于 Client；有无登录凭据、是否处于登录页属于 Browser；模板内容是否正确属于业务模板。一个 Profile 同时只允许一个写入任务，避免不同文档/任务争用焦点。

## 10. 复用唯一的 AutomationTask/Handler 体系

正式新增一个 TaskType（拟定 `tencent_sheet_fill`）以及一个 `TencentSheetFillTaskHandler : IAutomationTaskHandler`，按现有方式注册到 `AppServices.AutomationTaskHandlers`。前端在 `automationTaskTypes.tsx` 注册专用配置页，启停/删除和执行沿用已有入口。保留当前各业务独立的配置、调度与执行服务，不另建 Runner、Registry、通用 Step 或 Pipeline。

调用关系为：已有 `AutomationTaskRunner` → 新的 `TencentSheetFillTaskHandler` → 腾讯业务服务 → 已认证会话与 Sheet Client。通用 Runner 不知道模板内部步骤，只收最终 `AutomationTaskRunResult`。

原方案的 `ITencentSheetTemplateHandler` **只能是腾讯填报这个 TaskType 内部的模板策略，不是第二套自动化 Handler**。为了避免同名概念混淆，建议改称 `TencentSheetTemplate`。它负责根据业务日期和业务数据生成目标地址、数值、锚点预期及布局约束，不负责登录、调度、通知或运行历史。

首版只有一个生产月报模板，先用具体模板类/函数；不为单个实现建立接口和第二个模板注册中心。存在第二个实际模板并需要替换时，再抽取业务内部接口（如 `ITencentSheetTemplate`），仍不实现 `IAutomationTaskHandler`，也不出现在全局任务类型列表。

新类型遵守现有 `RuntimeEnvironment.Current.SchedulerEnabled` 环境隔离及通知约定，复用现有自动化 CLI 分发。正式实施仍需要该业务的任务配置、运行记录、调度入口和专用 UI；“复用外壳”不意味着这些业务能力已经存在。本轮仅明确边界，不改已有 DailyReport/NotionFill 行为。

## 正式实施的验收项

- 保存状态转换被捕获、转换太快未捕获、没有状态元素、保存中持续不结束、保存失败、重新打开仍为旧值；分别产生可解释结果，绝不重写恢复。
- 合并日期双列共用左上角、公司合并表头、隐藏列与合并叠加、非左上角配置读空；正确模板通过，错误锚点停止。
- 读取时网络抖动自动恢复；登录/权限/模板错误不重试；提交超时只读取确认；取消不恢复；一次运行只发最终通知。
- 日期函数覆盖业务时区午夜、月末/年末、闰年、周末、未知 mode、历史显式日期和跨日重试。
- 注册新 TaskType 后原 DailyReport/NotionFill 配置、调度和运行路径不变；Browser 登录判断只存在一处；模板不拥有调度或浏览器生命周期。

这些是后续验收要求，不是本轮通过的测试。当前用户反馈的随机数据写入成功与上述异常场景验收分别记录。
